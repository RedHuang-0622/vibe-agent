架构设计题：

模块一：Context / Performance
1.大模型面对第一轮长窗口或多模态输入时，first token 会显著变慢。有什么快速/低成本/用户体验也不差的方案？从5-10秒稳定压缩到2秒。
- ttft慢的主要原因是多模态理解时间和长上下文思考的时间。
- 那么我们对于多模态理解在用户上传完成多模态内容的时候就开始同步进行识别和特征提取，来省去发送之后串行理解多模态内容的时间
- 在模型侧设立上下文缓存机制，通过给前缀一个对应的向量，来减少同一前缀思考的时间，以deepseek的上下文kv缓存机制为例
- 同时请求的构建需要做出l1内存层的预热，不要等发送请求了再做请求的构建
- 在模型还没有产生 Token 时，前端可以先展示状态、处理阶段和已接收内容
2.一个 session 连续聊了 200 轮，context 快爆了。你会怎么做压缩？如何确保压缩后的对话仍然流畅？
- 设置窗口保护，保护tail n尾部轮次内容，压缩窗口之外的内容（不包括系统提示词）
- 上下文摘要分成三个部分，第一是前文对话轮次摘要，第二是重要任务条目列举，第三是当前未完成项

模块二：Memory
  1.和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题。Agent 如何做 memory 召回更合理？
- 作rag混合检索和关键字召回两步走，最终通过 Retrieval 得到 Top-K 候选，再进行 Reranking召回
-时间衰减：近期记忆适当提高权重。
- 重要性权重：用户长期偏好、关键决策优先。
- 记忆类型：事实、偏好、事件、任务、技术知识。
- 时间有效性：避免召回已经过时的决策。
- 来源追踪：保留原始对话引用，必要时回溯原文。
  2.你理解的 Agent memory 经典框架是什么？它的发展趋势是什么，最头部的玩家在怎么做？
- 是一个冷记忆是rag知识库检索，以及一个热记忆是一个活跃的memory看板
- 头部玩家和头部玩家主要的做法：
MemGPT / Letta：分层记忆与显式记忆管理。
LangGraph：短期状态与跨会话长期记忆。
Zep / Graphiti：时间知识图谱与记忆检索。
Mem0：记忆提取、更新与召回。

模块三：Task 
1.对于长程任务，大模型执行一段时间可能会忘掉目标，你知道哪些解决方案，有什么优缺？
- 设置一个任务看板，并且给任务设计里程碑，每个里程碑也是一个小的看板，然后根据里程碑派出subagent。mainagent负责整体的subagent调度工作和结果审查，如果subagent出现了崩溃或者中断，需要根据subagent会话最新的快照进行会话的中断恢复，同时通过git的worktree让subagent的工作空间隔离防止写文件的锁竞争。同时里程碑之间也有图关系拓扑来表示刚工作依赖
2.用户给 Agent 下达任务：每天早上 9 点根据昨天聊天情况做复盘总结。你会怎么设计？
- 定时脚本开启新一轮会话，让会话去完成任务工作，同时用户选择继续当前会话工作还是新开启一轮会话，以及需要的记忆分片装载和工作空间装载。同时时间根据系统时间确定具体的工作时间，同时支持用户根据时区进行调整
- 会话结束的结果返回需要确认结果的推送形式，默认是在会话中推送，但是需要支持用户自定义推送方式，比如在微信或者飞书等其他地方支持推送结果内容摘要

模块四：Tool / Session Runtime
1.Agent 工具有同步和异步两类。异步工具不能让用户一直等，但结果依然重要。你会如何设计异步工具执行和完成通知？
- 设计一个board记录异步工具调用内容，toolcall发送异步工具调用就是先在board上记录工具调用条目，之后异步工具完成工作之后做完成结果返回到会话后缀，返回会话后缀需要根据会话状态判定是先入消息缓冲队列还是直接插入，同时board做出销项，以及board支持持久化写入，方便会话中断恢复，同时tool calling结果写到消息缓冲队列也是如此
2.如果 session state 为 busy，此时用户又发来新消息，或者异步工具完成事件也到达，runtime 应该如何处理？
- 设计一个缓冲队列，将没法送出去的消息按照顺序排列到这个队列中，同时在reactloop下作消息队列的长度检查，一旦不为零就进行队列清空工作

模块五：Agent Runtime 架构对比
1.Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？他们各自这样设计的优缺点是什么？
- Anthropic 的工具调用采用结构化 Content Block,工具执行完毕后结果作为 tool_result Block 传回，使用 tool_use_id 对应原来的调用,而openai的格式更偏向toolcall
2.Openhands的状态机设计有什么优缺？更优雅的实现方式是怎么样的？
- 优点
通过 Action / Observation 统一 Agent 与 Runtime 的交互协议。
通过 EventStream 将执行流程事件化，降低 Agent 和 Runtime 的直接耦合。
状态变化可以被观察、记录和回放。
执行环境通过 Runtime 抽象，支持不同运行环境。
事件与状态持久化为会话恢复提供基础。
- 缺点
事件模型和状态投影之间需要保持一致。
异步事件的乱序、重复、丢失需要额外处理。
EventStream 如果同时承担事件总线、持久化和业务编排，会形成复杂度中心。
持久化执行记录不等于能够恢复所有执行现场。
工具执行中的外部副作用可能无法通过简单的事件回放撤销。
- 改进方案
分离 Session、Agent Run、Tool Task 三类生命周期。
使用 Append-only Event Log 作为执行事件记录。
使用 Snapshot + Replay 恢复状态。
通过统一的 State Transition Contract 管理状态迁移。
使用任务 ID、幂等键和执行结果关联处理异步工具。
采用 Master-Worker 调度，避免 Master 上下文成为任务进度的唯一来源
